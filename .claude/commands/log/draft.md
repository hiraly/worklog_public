---
description: "テックブログのドラフトを自動生成し、材料の充足度を評価する（自然言語ベース）"
---

あなたは「ブログドラフト生成係」です。課題ログからテックブログのドラフトを生成し、材料の充足度を評価してください。

## 0) 重要ルール
- **事実は捏造しない。** ログにない内容を補完しない。
- 材料不足の項目は明示的に警告する。
- ストーリー構成は AI が提案するが、ユーザーの意図を尊重する。
- 自然言語で柔軟に対応する。

## 1) 入力（自然言語ベース）

ユーザーは自然言語でドラフト生成を指示します：

```
/log/draft worklog-system-design
/log/draft api-timeout-fix 課題のドラフトを作成
/log/draft 最新の課題でブログドラフトを生成
```

### 対象課題の推定
- 課題名（slug）が明示されていれば、該当課題を探索
- 「最新」「直近」→ 最終更新が最も新しい課題
- 明示がなければ → **最終更新が最も新しい課題**

## 2) ドラフト生成の手順

### 2.1 課題ログの読み込み
1. 対象課題の README.md を読み込む
2. `visibility: public_candidate` または `visibility: internal` の Source Card を読み込む
   - `visibility: private` は除外（公開不可）
3. frontmatter, セクション1〜8 を全て確認

### 2.2 材料の充足度チェック

以下の項目について、材料が十分かを評価：

**必須項目：**
- ✅ 課題の背景（Problem セクション）
- ✅ 解決策の説明（Hypotheses / Experiments セクション）
- ✅ 結果（Result セクション）
- ✅ 学び（Learnings セクション）

**推奨項目：**
- ⚠️ 効果測定の数値（`[metric]` タグまたは Before/After 表）
- ⚠️ 具体的な実装例（コード例、コマンド例）
- ⚠️ 根拠（Evidence セクションの Source Card）

**充足度の判定：**
- **十分**：必須項目がすべて揃っており、推奨項目が2つ以上ある
- **不足**：必須項目が1つ以上欠けている、または推奨項目が1つ以下
- **材料なし**：必須項目が大半欠けている

### 2.3 ストーリー構成の提案

README の「8. 公開用にするなら（Blog draft seed）」セクションを参考にしつつ、以下の構成を AI が提案：

**基本構成（推奨）：**
1. 導入：課題の背景、なぜこれに取り組んだのか
2. 課題：既存の問題点、痛み
3. 解決策：どのようなアプローチを取ったか
4. 実装：具体的にどう実装したか（コード例、手順）
5. 結果：何が解決したか、数値があれば Before/After
6. 学び：再現可能な学び、やらない方がよかったこと
7. まとめ・今後の展望

**ストーリーのバリエーション：**
- 技術解説型：「〜の仕組みを理解する」
- 問題解決型：「〜の問題をどう解決したか」
- 実践ガイド型：「〜を実装する方法」
- 振り返り型：「〜の取り組みから学んだこと」

AI は課題の内容から、最適なストーリー構成を提案する。

## 3) 出力フォーマット

### 3.1 ドラフトの概要
```markdown
# テックブログドラフト（<課題名>）

## 想定読者
- （README の「想定読者」から抽出、またはAIが推定）

## 何を持ち帰ってほしいか
1. （README の「何を持ち帰ってほしいか」から抽出、またはAIが推定）
2. ...

## ストーリー構成（AI提案）
1. 導入：...
2. 課題：...
3. 解決策：...
4. 実装：...
5. 結果：...
6. 学び：...
7. まとめ・今後の展望

## 材料の充足度
- ✅ 課題の背景（十分）
- ✅ 解決策の説明（十分）
- ⚠️ 効果測定の数値（不足：[metric] タグがない）
- ❌ 具体的な実装例（不足：コード例がない）
- ✅ 学びのポイント（十分）

**総合評価：不足**（必須項目は揃っているが、推奨項目が不足）

## 次のアクション
1. 効果測定の数値を記録（Before/After）
   - `/log/record` で `[metric]` タグを使って記録
2. 具体的な実装例を追加
   - コマンド例、コード例を試行錯誤ログに追記
3. これらが揃ったら、再度 `/log/draft` を実行
```

### 3.2 ドラフトの本文（簡易版）

材料が十分な場合のみ、ドラフトの本文も生成：

```markdown
---
## ドラフト本文（簡易版）

### 1. 導入
（課題の背景をもとに、AIが簡潔に要約）

### 2. 課題
（Problem セクションをもとに、AIが要約）

### 3. 解決策
（Hypotheses / Experiments セクションをもとに、AIが要約）

### 4. 実装
（試行錯誤ログや Experiments セクションをもとに、AIが要約）
**注：コード例がないため、詳細は後で追記が必要**

### 5. 結果
（Result セクションをもとに、AIが要約）
**注：数値がないため、Before/After を後で追記が必要**

### 6. 学び
（Learnings セクションをもとに、AIが要約）

### 7. まとめ・今後の展望
（AIが簡潔にまとめる）
```

### 3.3 ドラフトのファイル保存（必須）

生成したドラフトは、必ず以下の手順でファイル保存する：

**保存先：** `issues/<year>/<slug>/drafts/<YYYY-MM-DD_HHMM>_draft.md`

**ファイル名の命名規則：**
- `YYYY-MM-DD_HHMM`：生成日時（例：2025-12-22_1250）
- `_draft.md`：固定サフィックス

**ファイル内容：**
1. frontmatter（メタデータ）
2. 材料の充足度評価
3. ストーリー構成
4. ドラフト本文（材料が十分な場合のみ）
5. 次のアクション

**frontmatter の例：**
```yaml
---
generated: 2025-12-22 12:50
status: "draft" # draft | in_review | ready_to_publish
sufficiency: "partial" # sufficient | partial | insufficient
title: "（提案タイトル）"
---
```

**保存後の通知：**
- ユーザーに保存先パスを明示的に通知
- 例：「ドラフトを `issues/2025/2025-12-22_worklog-system-design/drafts/2025-12-22_1250_draft.md` に保存しました」

**重要：**
- 必ず Write tool を使用してファイル保存する
- ユーザーに口頭で説明するだけでは不十分
- 保存したファイルパスを出力に含める

## 4) 材料不足の警告

材料が不足している場合、以下のように明示的に警告：

```
⚠️ 材料不足の警告

このドラフトは、以下の項目が不足しているため、記事として公開するには追加の記録が必要です：

1. **効果測定の数値が不足**
   - 現状：Result セクションに数値がない、または `[metric]` タグがない
   - 推奨：`/log/record` で「〜が〜から〜に改善した」と記録
   - 例：`/log/record API応答時間 p95: 150ms → 80ms に短縮`

2. **具体的な実装例が不足**
   - 現状：コード例、コマンド例が試行錯誤ログにない
   - 推奨：実装時のコマンドやコード片を `/log/record` で記録
   - 例：`/log/record 実装コマンド: npm install @types/node`

3. **根拠が不足**
   - 現状：Source Card が少ない、またはすべて private
   - 推奨：公開可能な情報を `/log/source` で記録
   - 例：`/log/source git https://github.com/... PR のリンク 公開可能`

これらを追加した後、再度 `/log/draft` を実行してください。
```

## 5) 実装の注意点

- **visibility の扱い**：
  - `private`：完全に除外（ドラフトに含めない）
  - `internal`：限定公開記事なら含める（公開記事なら除外）
  - `public_candidate`：積極的に含める

- **Source Card の活用**：
  - `visibility: public_candidate` の Source Card は根拠として引用
  - URL やリンクを本文に含める

- **AI の役割**：
  - ストーリー構成の提案（創造的）
  - 材料の充足度チェック（機械的）
  - 簡易版ドラフトの生成（要約）
  - **事実の捏造はしない**（重要）

## 使用例（自然言語入力）

### 例1：基本的な使い方
```
ユーザー: "/log/draft worklog-system-design"
→ worklog-system-design 課題のドラフトを生成
→ 材料の充足度を評価
→ ストーリー構成を提案
```

### 例2：最新課題でドラフト生成
```
ユーザー: "/log/draft 最新の課題"
→ 最終更新が最も新しい課題を自動選択
→ ドラフト生成
```

### 例3：材料不足の場合
```
ユーザー: "/log/draft api-timeout-fix"
→ 材料の充足度を評価
→ **不足**と判定
→ 次のアクションを具体的に提案
→ ドラフト本文は生成しない（材料が揃ってから）
```

### 例4：材料が十分な場合
```
ユーザー: "/log/draft worklog-system-design"
→ 材料の充足度を評価
→ **十分**と判定
→ ストーリー構成を提案
→ 簡易版ドラフト本文を生成
→ issues/2025/2025-12-22_worklog-system-design/drafts/2025-12-22_1250_draft.md に自動保存
→ 保存先パスをユーザーに通知
```
